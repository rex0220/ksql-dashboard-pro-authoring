# kSQL ダッシュボード設計レシピ集

> kintone-sql-tools の「kSQL バッチ設計レシピ集」の姉妹編。**ペイン(表示タイプ)ごとの定番 SQL パターン**を集める。
> テンプレートギャラリーの雛形 SQL、および設定画面ヘルプの原稿を兼ねる。

- 対応: kSQL エンジン **3.43 系**(read-only サブセット + バッチ)/ [設定ファイル仕様](./設定ファイル仕様.md) **1.14**
- 最終更新: 2026-08-04
- **改訂履歴は git を参照**(`git log --follow docs/ダッシュボードレシピ集.md`)
- `:変数` を使う「変数バインド版」は Pro Phase 2 の拡張文法(実装前)

### Pro プラグインで使えない構文(CLI / MCP 専用。実エンジンで確認)

kSQL の CLI・MCP には、**プラグインでは動かない拡張**がある。
AI や CLI で SQL を作ってペインへ貼るときは次に注意する。

| 構文 | ペインでの結果 |
| :--- | :--- |
| `APP4149@prod`(profile 指定) | PARSE_ERROR |
| `LAPP_案件管理`(論理アプリ参照) | 「未定義の論理アプリ」エラー(**プラグイン設定にマッピング機能が入るまでは `APP + 数字` で指定**してください) |
| `IMPORT CSV` / `IMPORT JSON` | 使用不可(ライブラリの境界外) |
| `EXPLAIN UPDATE` など DML の EXPLAIN | 使用不可(同上) |
| `UPDATE … VALIDATE ONLY` などの DML 事前検証 | 使用不可(同上) |
| `INSERT` / `UPDATE` / `DELETE` | READ_ONLY_VIOLATION |

**使えるもの**: `WITH`(CTE)、`UNION`、`SHOW` / `DESCRIBE`、
サブテーブル仮想テーブル `APP100$明細`、**`VALIDATE APP<番号>`**(D17)、
**`;` 区切りの複文・`CREATE TEMP TABLE` / `SET` / `DECLARE` / `ASSERT`**。

> **✅ 複文と一時テーブルはペインで使える。**
> ペインの実行を `runQuery` から **`runBatch`** へ移したため。
> **描画されるのは最後に結果セットを返した文**で、`CREATE TEMP TABLE` / `SET` / `DECLARE` は
> 結果を作らない。「集計してから最後に `SELECT` する」書き方がそのまま期待どおりになる。
>
> **一時テーブルは閲覧者のブラウザのメモリに載る。**1 表あたりの上限は既定 10,000 行
> (設定画面の詳細タブで 500〜10,000 に変更可。超過は常にエラー)。
> 同時に存在できるのは 16 表まで、寿命は**そのペインの 1 回の実行内だけ**で、
> **ペインをまたいだ共有はできない**。

### 前提フィールド

- `APP100` 案件管理: 受注日(日付)、受注金額(数値)、ステータス、部署、担当者、顧客名、顧客ランク(ドロップダウン)
- `APP200` 目標管理: 担当者、年月(文字列 `YYYY-MM`)、目標金額(数値)

| `markdown` | SQL は任意。**結果 1 行目**の列が本文の `{{列名}}` に入る | D13 | マークダウン | [§6.4](./設定ファイル仕様.md#64-markdown) |

グラフは 9 タイプあるが、**SQL の形は 4 通り**しかない — ①ラベル + 値(棒・横棒・円・ドーナツ)
②X 軸 + 値(折れ線・エリア)③ロング形式 3 列(積み上げ)④X 軸 + 値 2 本以上(複合)。

> **設定が参照するのは「結果の列名」。**`ksql_query`(または設定画面のプレビュー)が返した
> 列名をそのまま書く。**別名の英字は結果列名では小文字になる**(`AS ランクA` → `ランクa`)。
> 見出し・凡例の表示は SQL に書いたとおり出るが、`columns` / `totals` / `mapping` の参照は
> 小文字の側。フィールドコードとラベルが違う列は `AS` でラベルを付ける(設定ファイル仕様 §8)。

**横断する技術**(型に依らない)はレシピ側にある: JOIN(D10)、ログインユーザー・組織での
絞り込み(D14 / D14b)、ウィンドウ関数(D16)、`ROLLUP`(D18)、複文で構成比(D19)、
そして**ペインをまたぐ設計(S1〜S6)**。

### 用語 — 「押し下げ」(プッシュダウン)とは

以降で繰り返し出てくる言葉なので、先に定義しておく。

**kSQL は閲覧者のブラウザで動く。** kintone の REST API でレコードを取り寄せ、**取り寄せた後に
ブラウザの中で** SQL を評価する。このとき WHERE の一部は **kintone のクエリ文字列へ変換できる**。
変換できた条件は kintone のサーバー側で先に絞り込まれ、**残った分だけが返ってくる**。
これを**押し下げ**と呼ぶ。

```
押し下がる    SELECT … WHERE 受注日 = THIS_MONTH()
              → kintone へ「受注日 = THIS_MONTH()」を渡す → 該当分だけ受け取る

押し下がらない SELECT … WHERE 顧客名 LIKE '%商事%'
              → kintone へは何も渡せない → 全件受け取ってからブラウザで捨てる
```

**どちらでも結果は同じ。**変わるのは次の 2 点で、2 つ目が重要になる。

1. **取得件数**(通信量と時間)。REST は **1 リクエストあたり約 500 件**なので、
   10,000 件なら 20 往復、50,000 件なら 100 往復になる
2. **取得上限に当たるかどうか。** 上限(既定 10,000・最大 50,000)を超えると
   **集計はエラー**になる(原則 5。明細は打ち切り表示)。
   つまり押し下げは速度の話に留まらず、**そのペインが動くかどうかの話**になる

「動いていたのに、データが増えたら突然エラーになった」はこれが原因のことが多い。
**押し下がる書き方を選ぶ = 将来もエラーにならない書き方を選ぶ**、と考えてよい。

押し下げの対象は WHERE だけではない。`LIMIT`・`SELECT COUNT(*)`・`KORDER BY` も
kintone 側へ渡る。逆に、**フィールドを関数で包む**(`YEAR(受注日) = 2026`)と押し下げできなくなる。
述語ごとの可否は**押し下げ早見表**(この直後)を参照。

### 設計原則(ダッシュボード向け SQL)

1. **集計して小さく返す。** 描画に渡るのは集計後の行だけ。GROUP BY・LIMIT で行数を絞り、明細をそのまま返さない。
2. **1 ペイン 1 責務。** 1 つの SQL に複数の問いを詰め込まず、KPI と推移は別ペインに分ける。
   **押し下がる WHERE を揃えれば、別々の SQL でも取得は 1 回に統合される**(共有キャッシュ。
   キーは `アプリID + 押し下げ後の kintone クエリ`で、SQL 文字列ではない)。**S1** を参照。
3. **期間条件は kintone 相対日付関数を第一候補にする。** `TODAY()` / `THIS_MONTH()` /
   `THIS_YEAR()` / `FROM_TODAY(n, unit)` 等(WHERE 専用)は **kintone クエリへ変換(プッシュダウン)され、
   サーバー側で絞り込まれる**ため、取得レコード数そのものが減る。
   **集計・GROUP BY・ORDER BY を含むクエリでも使える。**
   OR で複数の相対日付を並べても、**WHERE 全体が押し下げ可能なら**動作する。
   **CTE(WITH)・一時テーブルの中でも使える。**
   **JOIN を含むクエリでも使える**(D10 参照)。次の 2 つの形が使える:
   - **A: WHERE 全体が片方のアプリだけを参照する形**(`OR` / `NOT` も可)
   - **B: `AND` でつないだ形** — 関数の部分だけがサーバーへ渡り、**複数アプリに分散していても
     それぞれのアプリへ渡る**。残りはクライアントで評価される
   使えないのは次のケース(実機確認。いずれも取得前エラー):
   - **`LEFT` / `RIGHT JOIN`**(外部結合)内の相対日付
   - **アプリをまたぐ `OR`**(`WHERE a.日付 = THIS_MONTH() OR t.更新日時 >= TODAY()`)
   - **CTE・一時テーブル・派生表を JOIN の入力にした形**
   - CTE 本体で、押し下げ不能な述語が AND で混ざる形
     (`WHERE 日付 = THIS_MONTH() AND LENGTH(件名) > 1`)。トップレベルなら可
   - KORDER BY / UPDATE・DELETE の対象選択 / サブテーブル

   これらでは `DATE_FORMAT()` / `YEAR()` / `MONTH()` による**ローカル評価**で書く(取得削減は効かない)。
4. **グルーピングキーは単純フィールドにする。** クロスフィルタ(Phase 2)を発行できるのは単純フィールド参照と日付粒度変換のみ(仕様案 §3.2)。
5. **取得上限に達したとき、集計はエラー・明細は打ち切り表示。**
   **集計は値そのものが誤る**ので、打ち切った値を出さずエラーにする。
   **明細の行は本物**なので、「全件ではない」と警告したうえで表示する。
   **この線引きはエンジンが行う。**対象は集計 / `GROUP BY` / `DISTINCT` /
   `UNION`(`ALL` なし)。**`UNION ALL` と素の明細は打ち切り表示**。
   上限は**ペインごとに 500〜10,000 件で設定できる**(設定画面の詳細タブ。既定 10,000)。
   上限に当たる場合は WHERE で期間を絞るか、`LIMIT` を付ける(`LIMIT` は kintone 側へ押し下がる)か、
   ペインの上限を上げる。ランキングや直近一覧のように一部しか見ないペインは、
   上限を小さくすると取得と描画が軽くなる。

   > **`SELECT COUNT(*)` は取得上限の影響を受けない。**
   > kintone が返す総件数を使い、**レコードを 1 件も取得せずに** 1 リクエストで返す。
   > **61 万件のアプリでも 676ms で総件数が出る**(実測)。
   > **総件数の KPI カードは、アプリの規模を気にせず書いてよい。**
   >
   > ただし適用されるのは **WHERE が完全に kintone 側へ押し下がる場合だけ**。
   > `LIKE` は JS 評価なので従来どおり全件取得になる(押し下げ早見表を参照)。
   > `GROUP BY` / `DISTINCT` / JOIN / `LIMIT` / `COUNT(列)` も適用外。
6. **GROUP BY にはエイリアスも書ける。**
   ただし**集計を含むエイリアス**(`COUNT(*) AS 件数` を `GROUP BY 件数`)は取得前エラーになる。
   同名の実フィールドがあればそちらが優先される(標準 SQL と同じ)。
   本レシピは曖昧さを避けるため **式指定**(`GROUP BY DATE_FORMAT(受注日, '%Y-%m')`)で統一する。
7. **`TODAY()` / `NOW()` / `LOGINUSER()` も相対日付と同じ扱い**(JOIN でも使える)。
   押し下げできない位置(OR で非押下述語と結合など)では**取得前エラー**になる。
   AND で非押下述語と組み合わせるのは可(押下部分だけサーバーへ送られる)。
8. **ユーザー系・複数選択系フィールドに `=` は使えない**(取得前エラーになる)。
   作成者 / 更新者 / ユーザー選択 / チェックボックス / 複数選択は **`in` / `not in`** を使う。
   **組織選択の `PRIMARY_ORGANIZATION()` も同じ**(D14b)。ただしこの関数だけは
   **優先組織が未設定の利用者では条件ごと無視され、全レコードが返る**。誰も気づけないので、
   使うときは前提をタイトルに書く。
9. **`SELECT *` は使わず、列を明示する。** ペインの設定(列の設定・条件付き書式・
   グラフの列割り当て)は**結果の列名を参照する**ため、`SELECT *` だと
   **kintone 側にフィールドを 1 つ追加しただけで結果の形が変わる**。
   取得フィールドも絞れないため、明示列のほうが軽い。
   0 行のときは明示列・`SELECT *` とも列が返り、ペインは「データなし」を表示する。
10. **ドロップダウン・ラジオボタン・ステータスは `=` でも動くが、`in` のほうが速い。**
   `=` は正しい結果を返すものの**押し下げされず全件取得になる**(単一表でも JOIN でも)。
   `in ('A')` と書くと kintone のクエリへ変換され、取得件数そのものが減る。
   実測(顧客 215 件): `顧客ランク = 'A'` → 215 件取得 / `顧客ランク in ('A')` → **59 件取得**。

> **相対日付関数の注意:** WHERE 専用。SELECT 列(CASE の条件など)では使えないため、
> 列側の期間判定には `CURRENT_DATE()` / `DATE_FORMAT()` / `YEAR()` / `MONTH()` を使う。
> **`DATE_ADD` の引数の形は MySQL と違う。**`DATE_ADD(列, n, '単位')` で、単位は
> `YEAR` / `MONTH` / `DAY`(大文字小文字は問わない)。減算は負数
> (`DATE_ADD(期限日, -1, 'MONTH')`)。**`DATE_SUB` と `INTERVAL` 構文は非対応。**
>
> 月・年の加減算で結果の日が対象月に存在しない場合は、**対象月の末日へ丸める**
> (`DATE_ADD('2026-01-31', 1, 'MONTH')` → `2026-02-28`)。MySQL 等と同じ。
>
> **丸めが起きると往復は元へ戻らない**(`1/31` → `2/28` → `1/28`)。これは丸めの
> 性質上避けられず、仕様として扱う。月の比較そのものを行うなら
> `YEAR(列) * 12 + MONTH(列)` の数値演算(D2)のほうが素直。
> **ウィンドウ関数は使える** — `ROW_NUMBER()` / `RANK()` / `DENSE_RANK()` の 3 つ(D16 参照)。
> ただし集計を伴うもの(`SUM(...) OVER ()` 等)は無い。
> `CURRENT_DATE()` / `CURRENT_TIMESTAMP()` は押し下げ経路がなく**実行環境のローカルタイムゾーン**で
> 評価される。kintone ドメインと時差がある環境では月初・月末の境界がずれ得るため、
> 期間の絞り込みには相対日付関数を優先する。
> 前月・前年の判定は `YEAR(列) * 12 + MONTH(列)` の数値演算で行う(D2 参照)。

### 押し下げ早見表 — フルスキャンを避ける

**フルスキャンは遅いだけでなくエラーになる。**取得上限(既定 10,000・最大 50,000)に達すると
**集計はエラー**、明細は打ち切り表示(原則 5)。「動いていたのに、データが増えたら突然
エラーになった」の原因はたいていここにある。

#### まず見るのは EXPLAIN の `fetch:` 行

**`mode: FULL_SCAN` は取得量の話ではない**(評価戦略の名前)。何件取りに行くかは `fetch` が名乗る
。設定画面の「実行計画(EXPLAIN)…」にも**「取得: …」の 1 行**が出る。

| `fetch` | 意味 |
| :--- | :--- |
| `count_only` | **件数のみ。**1 リクエストでレコードを走査しない(`SELECT COUNT(*)`) |
| `exact` | WHERE 全体が kintone 側へ渡った。**いちばん軽い絞り込み** |
| `prefiltered` | 一部だけ kintone 側で絞り、残りはブラウザで評価 |
| `all` | **全件取得。**取得上限に注意 |
| `none` | kintone から取得するソースが無い(一時テーブル参照のみ) |

`GROUP BY` や集計があると `mode` は必ず `FULL_SCAN` になる。**ダッシュボードのペインは
ほぼ全部そうなる**ので、`mode` だけを見て「重い」と判断しない。

#### 述語ごとの可否

> **正本はエンジンの言語リファレンス §6**(実装から生成・照合されている型 × 演算子表)。
> 下表はダッシュボード用途でよく使う組み合わせの早見版。

| 述語 | 単一表 | `INNER JOIN` | 備考 |
| :--- | :--: | :--: | :--- |
| 相対日付 / `TODAY()` / `LOGINUSER()` | **○** | **○** | `AND` なら複数アプリへ分散して渡る |
| `PRIMARY_ORGANIZATION()` | **○** | **○** | 組織選択 × `in` / `not in` のみ。**優先組織が未設定だと条件ごと無視される**(D14b) |
| 文字列の `=` | **○** | **○** | |
| `KLIKE`(kintone のキーワード検索) | **○** | **○** | `LIKE` とは別物。一致規則は kintone 準拠 |
| 選択系の `in ('A')` / `not in` | **○** | **○** | ドロップダウン・ラジオ・チェックボックス・複数選択・ステータス |
| 選択系の `=` | **✕** | **✕** | **kintone のクエリ文法が `in` / `not in` しか受け付けない**ため。原則 10 |
| `$id` / レコード番号の比較 | ○ | ○ | 5 演算子すべて可(正準な整数領域のため) |
| 数値の `=` / `>` / `<`(厳密比較) | ○ | **○** | |
| 数値の `>=` / `<=`(非厳密比較) | ○ | **✕** | **単一表なら押し下がる。**JOIN 内だけ不可(IEEE-754 の境界が理由) |
| 日付リテラルの範囲比較 | **○** | ✕ | `>= '2026-08-01' AND < '2026-09-01'` は単一表で `SIMPLE`(実測) |
| `LIKE` / `NOT LIKE` | **✕** | **✕** | **前方一致でも押し下がらない**(常に JS 評価。実測) |
| `IS NULL` / `IS NOT NULL` | **✕** | **✕** | 選択系の「未選択」は **`in ('')`** なら押し下がる(実測) |
| フィールドを関数で包む | **✕** | **✕** | `YEAR(受注日) = 2026` / `DATE_FORMAT(...)` など |
| `CURRENT_DATE()` / `CURRENT_TIMESTAMP()` | ✕ | ✕ | 押し下げ経路が無い。期間は相対日付関数で書く |

**単一表は「WHERE 全体を kintone クエリへ変換できれば型を問わず押し下がる」**のが原則で、
上表の ✕ が 1 つでも `OR` で混ざると全体が落ちる。**`AND` で混ざる場合は、押し下がる側だけが
prefilter に載る**(`fetch: prefiltered`)。

#### フルスキャンになる書き方 → 回避形

| フルスキャンになる | なぜ | 回避形 |
| :--- | :--- | :--- |
| `顧客ランク = 'A'` | 選択系の `=` は kintone が受け付けない | **`顧客ランク in ('A')`** — 実測 215 件取得 → **59 件** |
| `YEAR(受注日) = 2026` | フィールドを関数で包むと変換できない | **`受注日 = THIS_YEAR()`** |
| `受注日 >= CURRENT_DATE()` | 押し下げ経路が無い | 相対日付関数(`TODAY()` / `FROM_TODAY(...)`) |
| `顧客名 LIKE '%商事%'` | `LIKE` は常に JS 評価 | **`KLIKE`**、または押し下がる条件を `AND` で足して prefilter を効かせる |
| `詳細 IS NULL` | 押し下がらない | 選択系なら **`in ('')`**。テキストは絞り込みを別条件に頼る |
| `売上 >= 5000000`(JOIN 内) | 非厳密比較は JOIN で不可 | **`売上 > 4999999`** — 結果は同じまま押し下がる(主表のみ。実測 30 → 15 件) |
| `LEFT JOIN` の相手アプリ | 外部結合は結合キーで絞れない | `INNER JOIN` にできないか検討(下節) |

#### 例外 — `SELECT COUNT(*)` は上限の影響を受けない

`fetch: count_only`。**レコードを 1 件も走査せず** 1 リクエストで総件数を返す(原則 5)。
**61 万件のアプリでも 676ms**(実測)。総件数の KPI カードは規模を気にせず書いてよい。

ただし **WHERE が完全に押し下がる場合だけ**。`LIKE` が混ざれば従来どおり全件取得になる。

#### 確認の手順

1. **設定画面**: SQL 欄の「実行計画(EXPLAIN)…」→ 先頭の**「取得: …」**を見る
2. **MCP / CLI**: `ksql_explain` → `fetch summary:` と各ソースの `fetch:` 行
3. **一覧画面**: 診断ログ(`rex0220-kdp-debug`)の `rest` と `cacheHit`(S 系列冒頭)

**押し下げを揃えるとダッシュボード全体の取得も 1 回に統合される**が、揃えすぎと絞り込みは
衝突することがある(S4)。**取得上限を回避できる絞り込みは、全体最適より優先する。**

---

### 外部結合は取得上限に掛かりやすい

**`LEFT` / `RIGHT JOIN` を書くときは、取得上限を候補集合より大きくしてください。**
保持されない側(`LEFT` なら右)が上限に達すると、**エラーになって結果を返しません**。

打ち切ると「相手が見つからなかった」のか「上限の外へ落ちた」のかが**結果から区別できず、
どちらも空欄になる**ためです。エンジンが誤りを返さないよう止めています。

**結合キーによる絞り込み(押し下げ)は `INNER JOIN` だけが対象**で、外部結合が 1 つでも
混じると行われません。**相手のアプリを丸ごと取りに行く**ので、件数の多いアプリを
外部結合すると既定に近い上限でも掛かります。

- 対処: `WHERE` で候補を絞る / ペイン設定の**取得上限**を上げる
- **保持側だけが上限に達した場合**は従来どおり、警告付きで行を返します(行が減るだけで
  返した行そのものは正しいため)
- `INNER JOIN` は変わりません

## D1. KPI カード — 単一値

最小の形。予約列名が無ければ **1 列目がメイン値**になるため、`AS メイン値` は省略できる。

```sql
/* 今月 — THIS_MONTH() 単独条件は kintone クエリへ変換され、サーバー側で絞り込まれる */
SELECT SUM(受注金額)
FROM APP100
WHERE 受注日 = THIS_MONTH()
```

```sql
/* 明示する場合(他の列と併記するときは必要) */
SELECT SUM(受注金額) AS メイン値, COUNT(*) AS 件数
FROM APP100
WHERE 受注日 = THIS_MONTH()
```

```sql
/* カスタム期間・部署を外から与える変数バインド版(Phase 2) */
SELECT SUM(受注金額) AS メイン値
FROM APP100
WHERE 受注日 >= :START_DATE AND 部署 = :DEPT
```

## D2. KPI カード — 前月比を 1 クエリで

WHERE の相対日付 OR で**今月 + 先月だけをサーバー側から取得**し(押し下げ可能)、
列の振り分けは `YEAR()*12+MONTH()` の月キー演算で行う(年境界をまたいでも正しい)。
前月比(▲▼ %)は `メイン値` と `前月値`(または `基準値`)からペインが自動計算する。
テンプレート「KPI カード(合計 + 前月比)」と同じ方式。

```sql
SELECT
  SUM(CASE WHEN YEAR(受注日) * 12 + MONTH(受注日) = YEAR(CURRENT_DATE()) * 12 + MONTH(CURRENT_DATE())
      THEN 受注金額 ELSE 0 END) AS メイン値,
  SUM(CASE WHEN YEAR(受注日) * 12 + MONTH(受注日) = YEAR(CURRENT_DATE()) * 12 + MONTH(CURRENT_DATE()) - 1
      THEN 受注金額 ELSE 0 END) AS 前月値
FROM APP100
WHERE 受注日 = THIS_MONTH() OR 受注日 = LAST_MONTH()
```

- WHERE を省くと全期間を取得し、大規模アプリでは取得上限(既定 10,000 件)でエラーになる(原則 5)。
  相対日付で必ず絞ること。

## D3. 棒 — ステータス別件数

グルーピングキー(ステータス)が単純フィールドなので、クロスフィルタ(Phase 2)の起点にできる。

```sql
SELECT ステータス, COUNT(*) AS 件数
FROM APP100
WHERE 受注日 = THIS_YEAR()
GROUP BY ステータス
ORDER BY 件数 DESC
```

- 上位だけ見たい場合は `LIMIT 10` を足す(Top N 棒)。棒の幅・間隔はペイン側が自動調整する。

## D4. 積み上げ棒 — 月次 × ステータス

2 キーの GROUP BY(ロング形式)。表示タブの「列の割り当て」で X 軸 = 年月、系列キー = ステータス、
値 = 件数 を指定する(テンプレート「月次 × 分類(積み上げ)」は自動設定済み)。

```sql
SELECT DATE_FORMAT(受注日, '%Y-%m') AS 年月, ステータス, COUNT(*) AS 件数
FROM APP100
WHERE 受注日 = THIS_YEAR()
GROUP BY DATE_FORMAT(受注日, '%Y-%m'), ステータス
ORDER BY 年月
```

**返る列 → 設定**(積み上げは `mapping` が必須)

`mapping` を省略すると**ワイド形式として解釈される** — 1 列目が X 軸、数値列だけが系列に
なり、系列キーの列(`ステータス`)は無視される。同じ年月の行がそのまま並び、積み上がらない。

| 返る列 | 役割 | 書く場所 |
| :--- | :--- | :--- |
| `年月` | X 軸 | `mapping.x` |
| `ステータス` | 系列キー | `mapping.seriesKey` |
| `件数` | 値 | `mapping.value` |

```jsonc
"options": { "mapping": { "x": "年月", "seriesKey": "ステータス", "value": "件数" } }
```

- **系列キーは必ず集計後の少数の値にする。**明細のまま(顧客名など一意に近い列)を系列に
  すると系列が行数まで増える。8 本を超えた分は「その他」へ畳まれるので、意図した絵にならない

## D5. 折れ線 — 月次推移

```sql
SELECT DATE_FORMAT(受注日, '%Y-%m') AS 年月, SUM(受注金額) AS 売上
FROM APP100
WHERE 受注日 = THIS_YEAR()
GROUP BY DATE_FORMAT(受注日, '%Y-%m')
ORDER BY 年月
```

- 週次は `DATE_FORMAT(受注日, '%G-%v')`(ISO 週)、四半期は `QUARTER(受注日)` を使う。
- GROUP BY は式をそのまま書く(原則 6。`GROUP BY 年月` は誤集計になる)。

## D6. 折れ線 2 系列 — 今年 vs 前年

WHERE の相対日付 OR で 2 年分をサーバー側から取得し、`CASE` で年を列に分ける。
年をハードコードしないので年が変わっても書き換え不要。

```sql
SELECT
  MONTH(受注日) AS 月,
  SUM(CASE WHEN YEAR(受注日) = YEAR(CURRENT_DATE())     THEN 受注金額 ELSE 0 END) AS 今年,
  SUM(CASE WHEN YEAR(受注日) = YEAR(CURRENT_DATE()) - 1 THEN 受注金額 ELSE 0 END) AS 前年
FROM APP100
WHERE 受注日 = THIS_YEAR() OR 受注日 = LAST_YEAR()
GROUP BY MONTH(受注日)
ORDER BY 月
```

- 押し下げが効かない書き方(JOIN 併用など)にする場合は、`WHERE YEAR(受注日) >= YEAR(CURRENT_DATE()) - 1`
  のローカル条件で代替できる(取得削減は効かない)。

## D7. 円 / ドーナツ — 構成比

SQL は単純な GROUP BY でよい。「上位 N + その他」への集約はペインの表示オプションが行う(§4.10)。

```sql
SELECT 部署, SUM(受注金額) AS 売上
FROM APP100
WHERE 受注日 = THIS_MONTH()
GROUP BY 部署
```

## D8. 明細表 + 集計行

集計行(合計・平均)・条件付き書式はペイン機能なので SQL は明細を返すだけでよい。
レコードを開くアイコン列(§4.6)を使う場合は `$id` を含める。

```sql
SELECT $id, 受注日, 顧客名, 担当者, ステータス, 受注金額
FROM APP100
WHERE 受注日 = THIS_MONTH()
ORDER BY 受注金額 DESC
LIMIT 500
```

- 明細表は行数が増えやすい唯一のペイン。**LIMIT を明示**して取得上限より十分小さく保つ。
- 列幅・表示名・集計行は「列の設定…」、閾値ハイライト・ヒートマップは「条件付き書式…」で GUI 設定できる。

**返る列 → 設定**(`columns` / `totals` / `rules` の**キーは結果の列名**)

```jsonc
"options": {
  "columns": { "受注金額": { "align": "right", "format": { "prefix": "¥", "thousands": true } },
               "$id": { "width": 90 } },
  "totals":  { "受注金額": "sum" }
}
```

- キーを間違えても**エラーにならず黙って無視される**(`options` はバリデータを素通りする)。
  効かないときはまず列名を疑う

## D9. 複合(2 軸)— 売上(棒)と件数(線)

1 つの GROUP BY で 2 つの測定値を返す。棒 / 線の割り当ては表示タブの「列の割り当て」で変更可能
(既定: 最初の数値系列が棒 = 左軸、残りが線 = 右軸)。

```sql
SELECT DATE_FORMAT(受注日, '%Y-%m') AS 年月,
       SUM(受注金額) AS 売上,
       COUNT(*)     AS 件数
FROM APP100
WHERE 受注日 = THIS_YEAR()
GROUP BY DATE_FORMAT(受注日, '%Y-%m')
ORDER BY 年月
```

**返る列 → 設定**(既定でも描けるが、どちらを棒にするかは明示したほうが確実)

```jsonc
"options": {
  "bars": ["売上"], "lines": ["件数"],
  "valueFormat":      { "prefix": "¥", "thousands": true },   // 左軸(棒)
  "valueFormatRight": { "suffix": " 件" }                      // 右軸(線)
}
```

- **`valueFormatRight` は `valueFormat` を継承しない。**省略すると素の数値になる。
  金額と件数を並べる複合では、継承すると常に誤りになるための仕様
- 値列は 2 本以上必要。1 本しか返さないと複合にならない

## D10. 担当者別 実績 × 目標(JOIN + 達成率)

目標アプリと結合し、達成率を計算する。**JOIN でも相対日付が使える**ので、
期間は `THIS_MONTH()` で書く。これで**案件側がサーバー側で当月分だけに絞られる**。

```sql
SELECT a.担当者,
       COUNT(*)                             AS 受注件数,
       SUM(a.受注金額)                       AS 売上金額,
       SUM(a.受注金額) * 100 / MAX(t.目標金額) AS 達成率
FROM APP100 a
JOIN APP200 t
  ON a.担当者 = t.担当者
WHERE a.受注日 = THIS_MONTH()
  AND t.年月 = DATE_FORMAT(CURRENT_DATE(), '%Y-%m')
GROUP BY a.担当者
ORDER BY 達成率 DESC
```

- 達成率列に「条件付き書式…」で閾値(例: `< 90` → 重大)やヒートマップを設定すると一目で分かる。
- `t.年月` は文字列比較なので押し下げ対象(押し下げ早見表)。ただし右辺が `DATE_FORMAT(CURRENT_DATE(), …)` の
  **関数呼び出しのままだと押し下がらない**ことがある。相手側も確実に絞りたい場合は
  `t.年月 = '2026-07'` のようなリテラル、または相対日付が使える日付フィールドを用意する。

### JOIN での押し下げ — アプリごとに絞る

述語ごとの可否は**押し下げ早見表**(設計原則の直後)にまとめた。JOIN で単一表と違うのは
次の 2 点だけである。

- **数値の `>=` / `<=` は JOIN 内では押し下がらない。**厳密比較へ書き換える —
  整数値なら `売上 >= 5000000` → **`売上 > 4999999`** で結果は同じまま効く
  (実測: 主表の取得が 30 件 → 15 件)。**効くのは述語を書いた側だけ**で、
  **結合先は全件のまま**。相手も絞るならそちらにも WHERE 条件を付ける
- **押し下げが効くのは `INNER JOIN` だけ。**外部結合が 1 つでも混じると、結合キーによる
  絞り込みが行われず相手を丸ごと取りに行く(下節)

**述語が付いていないアプリは全件取得のまま**である。結合相手側も絞りたい場合は、
そちらにも WHERE 条件を付ける。

```sql
/* 両アプリとも絞られる形(実測: 全 235 件 → 79 件取得) */
WHERE a.受注日 = THIS_MONTH()      -- APP100 へ
  AND t.区分 in ('A')              -- APP200 へ
```

## D11. KPI 複数行タイル — ランク別の一覧

表示タブの「**複数行をタイル表示**」をオンにすると、結果の各行がミニタイルで並ぶ。
予約列の無い 2 列結果は「1 列目 = ラベル、2 列目 = 値」と自動解釈される。

```sql
/* 最小: ランク別件数のタイル */
SELECT 顧客ランク, COUNT(*) AS 件数
FROM APP100
GROUP BY 顧客ランク
ORDER BY 件数 DESC
```

```sql
/* タイルごとに前月比(▲▼ %)まで出す版: タイトル / メイン値 / 基準値 の 3 列 */
SELECT
  顧客ランク AS タイトル,
  SUM(CASE WHEN YEAR(受注日) * 12 + MONTH(受注日) = YEAR(CURRENT_DATE()) * 12 + MONTH(CURRENT_DATE())
      THEN 受注金額 ELSE 0 END) AS メイン値,
  SUM(CASE WHEN YEAR(受注日) * 12 + MONTH(受注日) = YEAR(CURRENT_DATE()) * 12 + MONTH(CURRENT_DATE()) - 1
      THEN 受注金額 ELSE 0 END) AS 基準値
FROM APP100
WHERE 受注日 = THIS_MONTH() OR 受注日 = LAST_MONTH()
GROUP BY 顧客ランク
ORDER BY 顧客ランク
```

- 1 番目の例のように WHERE を省くと全期間を取得する。件数の多いアプリでは
  取得上限(原則 5)でエラーになるため、**相対日付で必ず絞る**こと。

- 「条件付きカラー…」の閾値はタイル単位で評価される(例: メイン値 < 20 → 重大で赤タイル)。
- 最大タイル数は既定 8(表示タブで変更。超過分は「他 N 件」)。

## D12. Top N ランキング表

```sql
SELECT 担当者, COUNT(*) AS 件数, SUM(受注金額) AS 売上
FROM APP100
WHERE 受注日 = THIS_MONTH()
GROUP BY 担当者
ORDER BY 売上 DESC
LIMIT 10
```

- 表タイプで使い、「列の設定…」で売上列に合計・フォーマット(¥・3 桁区切り)を設定する。
- 構成比列(全体比 %)は**単文では出せない**が、複文なら書ける(D19)。(`SUM(...) OVER ()` も集計を含むスカラー
  サブクエリも無い)。割合はドーナツ(D7)で見せる。**`runBatch` を使えば `SET @total` で出せる**(D19)。
- **順位を列として出したい場合は D16**(ウィンドウ関数)。単純な上位 N は本レシピの LIMIT で足りる。
- **小計・総計行は D18**(ROLLUP)。**Top N + その他** は D19。

## D13. マークダウン — 動的な説明文

マークダウンペインは SQL 任意。埋め込み用 SQL を設定すると本文の `{{列名}}` が
結果 1 行目の値に、`{{rowCount}}` が行数に置き換わる。

埋め込み用 SQL:

```sql
SELECT COUNT(*) AS 件数, SUM(受注金額) AS 合計
FROM APP100
WHERE 受注日 = THIS_MONTH()
```

本文(マークダウン):

```markdown
## 今月のサマリー

今月の受注は **{{件数}}** 件、合計 **{{合計}}** 円です。

- 集計対象: 受注日が今月のレコード
- <span style="color: red">数値は 10 分ごとに自動更新されます</span>
```

- style 属性は装飾系プロパティ(color / background-color / text-align 等)のみ有効。
- **埋め込み値に数値フォーマットは適用されない。** マークダウンペインには書式オプションが無いため、
  `{{合計}}` は SQL が返した生の値(例 `3900`)のまま表示される。桁区切りや通貨記号を付けたい場合は
  **SQL 側で文字列に整形して返す**(例: `CONCAT('¥', FORMAT(SUM(受注金額), 0)) AS 合計` — 利用できる
  関数は kSQL 言語リファレンスを確認)。金額を見栄えよく出すなら KPI カード(D1・D2)が適する。

## D14. 自分の担当分だけ表示(ログインユーザー絞り込み)

`LOGINUSER()` は **`in` / `not in` で使える**(作成者 / 更新者 / ユーザー選択が対象)。
`作成者 in (LOGINUSER())` の形でサーバーへ送られ、kintone 側が解決するため取得も減る。

```sql
/* 自分が作成したレコードの件数 */
SELECT COUNT(*) FROM APP100 WHERE 作成者 in (LOGINUSER())
```

```sql
/* 自分の担当案件を一覧表示(担当 = ユーザー選択フィールド) */
SELECT $id, 顧客名, ステータス, 受注金額
FROM APP100
WHERE 担当 in (LOGINUSER()) AND 受注日 = THIS_MONTH()
ORDER BY 受注日 DESC
LIMIT 200
```

- **`=` は使えない**(原則 8)。ユーザー系・複数選択系は必ず `in` / `not in`
- `in (LOGINUSER(), 'taro')` のような**他の値との混在は不可**(単独要素のみ)
- グループ選択フィールドには使えない(kintone 公式の制約)
- 共通ダッシュボードに置くと、閲覧者ごとに内容が変わる「マイダッシュボード」になる

## D14b. 自組織のデータだけ表示(優先組織で絞り込み)

`PRIMARY_ORGANIZATION()` は `LOGINUSER()` と同じ位置づけで、
**組織選択フィールド**に対して `in` / `not in` の**単独要素**として書く。

```sql
/* 自組織の受注金額 */
SELECT SUM(売上) AS メイン値
FROM APP100
WHERE 担当組織 in (PRIMARY_ORGANIZATION()) AND 商談フェーズ = '受注'
```

- 対象は**組織選択フィールドのみ**。演算子は **`in` / `not in` のみ**。他の値との混在は不可
  (いずれもレコード取得前にエラー)
- kintone サーバーへ素通しされるため、取得件数も減る(`EXACT_PUSHDOWN`)
- **DML の `WHERE` では使えない**(条件が無視されるとアプリ全件が対象になるため、静的に拒否される)

### ⚠ 優先組織が未設定の利用者では、絞り込みが効かない

**kintone の仕様。** API を実行したユーザーに優先する組織が設定されていない場合、
`組織 in (PRIMARY_ORGANIZATION())` は**無視され、他の条件を満たす全レコードが返る**。

ダッシュボードでは、**「自組織の実績」のつもりの数字が、その利用者には全社の数字として見える**。
**エンジンからも Pro からも、条件が無視されたことは判別できない。**警告も出せない。

Pro は 2 か所で伝える。役割が違う。

| 画面 | 相手 | 内容 |
| :--- | :--- | :--- |
| **設定画面** | 書く人 | SQL にこの関数が含まれると注意書きを出す。**前提**の告知 |
| **一覧画面** | 見る人 | 優先組織が**無い利用者にだけ**、そのペインへ警告を出す。**事実**の表示 |

一覧画面では `kintone.user.getOrganizations()` で優先組織の有無を確かめる
(一般利用者の権限で動く。プラグイン設定画面では使えないため、閲覧側だけ)。
判断できない場合(API が無い・失敗した)は**何も出さない** — 誤った警告は、警告が無いことより悪い。

そのうえで、書く側でも次のどちらかを取る。

1. **ペインのタイトルに前提を書く** — `自組織の受注金額（優先組織の設定が前提）`
2. **配布前に、対象の利用者に優先組織が設定されていることを確認する**

**確かめ方**(管理者が 1 回だけ実行する。常時の検査には重い):

```sql
SELECT COUNT(*) FROM APP100 WHERE 担当組織 in (PRIMARY_ORGANIZATION())
SELECT COUNT(*) FROM APP100 WHERE 担当組織 not in (PRIMARY_ORGANIZATION())
```

正常なら `in + not in ≤ 全件`。**両方が全件と一致したら、条件が落ちている**
(正常時には起こらない組み合わせ)。

## D15. クロスフィルタと相性の良い書き方(Phase 2 先行ガイド)

> **クロスフィルタは未実装(Phase 2 予定)。** 下表は実装時に連動の起点にできるかどうかの
> 見通しであり、現時点でクリックしても絞り込みは行われない。

| 書き方 | 連動の起点になるか |
| :--- | :--- |
| `GROUP BY ステータス`(単純フィールド) | ○ クリックで他ペイン・一覧を絞り込める |
| `GROUP BY DATE_FORMAT(受注日, '%Y-%m')`(日付粒度) | ○ 粒度付きフィルタとして発行される |
| `GROUP BY CASE WHEN 金額 >= 1000000 THEN '大型' ... END`(導出列) | ✕ 発行不可(クリック不可表示) |
| JOIN / UNION を含むクエリのグルーピングキー | ✕ 発行不可。受け側(accepts)としてのみ連動可 |

- 金額帯などの区分で連動させたい場合は、kintone 側に区分フィールドを持たせて単純フィールド化するのが確実。

## D16. ランキング — ウィンドウ関数で順位列を出す

使えるのは **`ROW_NUMBER()` / `RANK()` / `DENSE_RANK()`** の 3 つ(実エンジン検証済み)。
構文は `関数() OVER (PARTITION BY ... ORDER BY ...) AS 別名` に固定で、
**`OVER (...)` と `AS 別名` はいずれも省略不可**(省略すると PARSE_ERROR)。

| 関数 | 同点の扱い |
| :--- | :--- |
| `ROW_NUMBER()` | 同点でも連番(1, 2, 3) |
| `RANK()` | 同点は同順位・次が飛ぶ(1, 2, 2, 4) |
| `DENSE_RANK()` | 同点は同順位・次が飛ばない(1, 2, 2, 3) |

**集計・GROUP BY と同じ SELECT には書けない**(`ウィンドウ関数は GROUP BY / 集計関数と同じ
SELECT では使用できません`)。集計してから順位を付けるには CTE で段を分ける。

```sql
/* 担当別 売上ランキング Top 5 */
WITH 集計 AS (
  SELECT 担当者, COUNT(*) AS 件数, SUM(受注金額) AS 売上
  FROM APP100
  WHERE 受注日 = THIS_MONTH()
  GROUP BY 担当者
),
順位付き AS (
  SELECT 担当者, 件数, 売上,
         RANK() OVER (ORDER BY 売上 DESC) AS 順位
  FROM 集計
)
SELECT 順位, 担当者, 件数, 売上
FROM 順位付き
WHERE 順位 <= 5
ORDER BY 順位
```

```sql
/* グループごとの上位 N(LIMIT では書けない形) */
WITH 集計 AS (
  SELECT 部署, 担当者, SUM(受注金額) AS 売上
  FROM APP100
  WHERE 受注日 = THIS_MONTH()
  GROUP BY 部署, 担当者
),
順位付き AS (
  SELECT 部署, 担当者, 売上,
         RANK() OVER (PARTITION BY 部署 ORDER BY 売上 DESC) AS 順位
  FROM 集計
)
SELECT 部署, 順位, 担当者, 売上
FROM 順位付き
WHERE 順位 <= 3
ORDER BY 部署, 順位
```

- **最後の `ORDER BY` は必須。** 順位は列として計算されるだけで、行の並び順は変わらない。
- `OVER (ORDER BY ...)` の中に集計関数は書けない(`OVER (ORDER BY SUM(金額))` は PARSE_ERROR)。
- **JOIN との併用は可。** WHERE の相対日付も効き、押し下げも維持される(検証済み)。
- 単純な上位 N(順位列が不要)なら `ORDER BY ... LIMIT N` で足りる(D12)。
- GROUPING SETS / ROLLUP と併用すると `B65 window functions are not supported in Phase1` になる。

## D17. データ品質チェック — `VALIDATE`

`VALIDATE APP<番号>` は**フォームの入力規則に違反している既存レコードを洗い出す**。
`SELECT` と同じくペインで実行できる(単文なので `runQuery` で動く)。

```sql
VALIDATE APP100
```

**返る列(9 列)**

| 列 | 内容 |
| :--- | :--- |
| `$id` | レコード ID(**表ペインならレコード遷移アイコンが出る**) |
| `$err_field` / `$err_code` / `$err_message` | 違反したフィールド・コード・メッセージ |
| `$err_value` | 実際に入っていた値 |
| `$err_subtable` / `$err_subrow` / `$err_subrow_id` | サブテーブル内の違反位置 |
| `$err_count` | **その行が表すエラーの本数**(サブテーブルは複数がまとまる) |

**検出できる違反**: 必須漏れ / 文字数(min・max)/ 数値の上下限 / 定義外の選択肢 / 日付・時刻の形式。

- **KPI カード**にはエラー件数をそのまま出せる(結果に `validateStats` が付き、集計済みで返る)
- **表ペイン**にすれば診断行がそのまま一覧になる。`$id` があるのでレコードへ飛べる
- **エラーコード別の内訳グラフ**は `VALIDATE ... INTO #err` → `GROUP BY` の複文で書ける

> **集計は `COUNT(*)` ではなく `SUM($err_count)` を使う。** サブテーブルの違反は
> 1 行に複数エラーがまとまるため、`COUNT(*)` だとエラー総数と一致しない
> (実測: `COUNT(*)` = 10 / `SUM($err_count)` = 12)。

> **検証範囲は `validateStats.constraintMetadata` で確認できる。**
> `present` / `absent` に、どの種類の制約を見たかが入る。
> 「0 件 = 本当に問題なし」なのか「その種類を見ていないだけ」なのかを区別できる。

## D18. 小計・総計を SQL で作る — `ROLLUP` / `GROUPING`

**単文なので、複文を書かなくてもペインで使える。**
表ペインの「集計行」は末尾の総計だけだが、`ROLLUP` なら**グループごとの小計**も出せる。

```sql
/* フェーズ別 + 総計行 */
SELECT CASE WHEN GROUPING(商談フェーズ) = 1 THEN '【総計】' ELSE 商談フェーズ END AS 区分,
       SUM(売上) AS 売上,
       COUNT(*)  AS 件数
FROM APP100
WHERE 商談フェーズ <> ''
GROUP BY ROLLUP(商談フェーズ)
```

| 区分 | 売上 | 件数 |
| :--- | ---: | ---: |
| 提案中 | 28,250,000 | 6 |
| 内示 | 12,750,000 | 2 |
| 受注 | 40,800,000 | 8 |
| **【総計】** | **81,800,000** | **16** |

- `GROUPING(列) = 1` が**小計・総計の行**を表す。`CASE` でラベルを付けると読みやすい
- 2 階層も可: `GROUP BY ROLLUP(商談フェーズ, 提案商品)` で「フェーズ小計 + 総計」が入る
- **ラベルを付けないと小計行の該当列が空文字になる**ため、表ペインでは区別が付きにくい

## D19. 構成比・Top N + その他 — 複文で書く

**`SET @変数 = (SELECT ...)` を使うと、これまで「SQL では出せない」としていた形が書ける。**
**複文だがペインでそのまま実行できる**(ペインは `runBatch` で実行される)。

**描画されるのは最後の `SELECT`** で、`CREATE TEMP TABLE` と `SET` は結果を作らない。

```sql
/* 全体比 %(構成比列) */
CREATE TEMP TABLE #g AS
  SELECT 提案商品, SUM(売上) AS 売上 FROM APP100 WHERE 提案商品 <> '' GROUP BY 提案商品;
SET @total = (SELECT SUM(売上) FROM #g);
SELECT 提案商品, 売上, ROUND((売上 * 100) / @total, 1) AS 構成比 FROM #g ORDER BY 売上 DESC;
```

→ 商品C **43.1** / 商品B **31.7** / その他 **12.7** / 商品A **12.5**(実測)

```sql
/* Top 3 + その他の合算(表でも使える。円の topN オプションと違い任意の表示タイプで可) */
CREATE TEMP TABLE #r AS SELECT 会社名, SUM(売上) AS 売上 FROM APP100 GROUP BY 会社名;
CREATE TEMP TABLE #t AS SELECT 会社名, 売上 FROM #r ORDER BY 売上 DESC LIMIT 3;
SET @other = (SELECT SUM(売上) FROM #r WHERE 会社名 NOT IN (SELECT 会社名 FROM #t));
SELECT 会社名, 売上 FROM #t
UNION ALL SELECT 'その他' AS 会社名, @other AS 売上 FROM #t LIMIT 1;
```

> **変数はそのまま算術に使える。** `(売上 * 100) / @total` と書ける。
> 小数桁を丸めたい場合は `ROUND((売上 * 100) / @total, 1)`、
> 比率(0〜1)で返してペインの `%` 表示に任せるなら `ROUND((売上 * 1.0) / @total, 4)`。

# ペインをまたぐ設計(S1〜S6)

D1〜D19 は **1 ペイン 1 本**の SQL パターン。ここからは**ダッシュボード 1 枚**を単位にする。
「同じデータを複数のグラフ・表で見せたい」「期間を 1 か所で切り替えたい」はここで扱う。

## まず仕組み — 何が共有されるのか

**共有キャッシュのキーは `アプリID + 押し下げ後の kintone クエリ`。SQL 文字列ではない。**
ここを取り違えると設計を誤るので、先に押さえる。

1. **同じ SQL を貼る必要はない。** 押し下がる WHERE が同じなら、SELECT も GROUP BY も
   表示タイプも違ってよい。KPI・棒・折れ線・表の 4 枚が**別々の SQL でも取得は 1 回**になる
2. **逆に 1 ペインだけ押し下がる条件を足すと、そのペインは別キーになり取得が増える**
3. **押し下がらない条件(`LIKE` など)で絞ってもキーは変わらない。**
   「押し下げ = 常に善」ではない — 単ペインでは取得が減るが、**ダッシュボード全体では
   キャッシュを分ける方向に働く**ことがある(原則 3 と衝突する場面。S4)
4. **参照する列が違うと、和集合で取り直すことがある。** 条件が同じでも、後から来たペインが
   既存のキャッシュに無い列を要求すると 1 回増える。ペイン数ぶん増えることはない
5. **一時テーブル(`CREATE TEMP TABLE`)はペインをまたげない。**寿命はそのペインの 1 回の実行内(S6)

### 取得回数を実際に数える

診断ログを出すと、ペインごとに `cacheHit` が出る。**「1 回に統合された」は主張ではなく
実測できる**。一覧画面のコンソールで:

```js
localStorage.setItem('rex0220-kdp-debug', '1');   // 1 回だけ。以後は不要
location.reload();
```

```
[kSQL Pro] pane=kpi1  rows=1  total=421ms rest=380ms engine=12ms cacheHit=false
[kSQL Pro] pane=bar1  rows=8  total=402ms rest=0ms   engine=9ms  cacheHit=true
[kSQL Pro] pane=line1 rows=12 total=404ms rest=0ms   engine=11ms cacheHit=true
```

`rest=0ms` かつ `cacheHit=true` が「取りに行っていない」ペイン。

## S1. 同一期間の KPI・グラフ・表を 1 取得で回す

**押し下がる WHERE を全ペインで揃える。**これだけで REST 取得が 1 回に集約される。

```sql
/* ペイン 1: KPI(今月の売上) */
SELECT SUM(受注金額) AS メイン値 FROM APP100 WHERE 受注日 = THIS_MONTH()
```

```sql
/* ペイン 2: 棒(ステータス別件数) */
SELECT ステータス, COUNT(*) AS 件数 FROM APP100 WHERE 受注日 = THIS_MONTH()
GROUP BY ステータス ORDER BY 件数 DESC
```

```sql
/* ペイン 3: 表(明細) */
SELECT $id, 顧客名, ステータス, 受注金額 FROM APP100 WHERE 受注日 = THIS_MONTH()
ORDER BY 受注金額 DESC LIMIT 100
```

- 3 本とも `受注日 = THIS_MONTH()` で**押し下げ後のクエリが同一**になり、取得は統合される
- ペイン 3 は他が使わない列(`顧客名` など)を要求するため、**列の和集合で取り直しが 1 回
  入ることがある**。それでも 3 回にはならない
- **やってはいけないのは、同じ「今月」を別の書き方で表すこと。**
  `WHERE 受注日 = THIS_MONTH()` と `WHERE DATE_FORMAT(受注日,'%Y-%m') = DATE_FORMAT(CURRENT_DATE(),'%Y-%m')`
  は結果が同じでもキーが別になる。後者は押し下がらないので**全件取得**にもなる

## S2. 同じ集計を「グラフで俯瞰 + 表で数字」の 2 枚に出す

グラフは大小が一目で分かるが正確な値は読めない。表はその逆。**両方出すのが定石**で、
このとき SQL は**同じものを 2 つのペインに複製する**。

```sql
/* 2 ペインとも同じ SQL。type だけ変える */
SELECT 部署, SUM(受注金額) AS 売上, COUNT(*) AS 件数
FROM APP100
WHERE 受注日 = THIS_YEAR()
GROUP BY 部署
ORDER BY 売上 DESC
```

| ペイン | type | 表示側の設定 |
| :--- | :--- | :--- |
| 俯瞰 | `bar` | `mapping: { x: "部署", value: "売上" }` |
| 数字 | `table` | `columns` で `売上` に通貨書式、`totals: { "売上": "sum", "件数": "sum" }` |

- **重複を嫌って 1 本にまとめようとしない。**集計結果をペイン間で受け渡す仕組みは無い(S6)。
  SQL は複製し、**取得だけ共有させる**のが正しい。条件も列も同一なので確実に 1 回で済む
- 表側だけ `LIMIT` を足すと**押し下げが変わってキーが割れる**(`LIMIT` は kintone 側へ渡る)。
  上位だけ見せたいなら、SQL ではなくグラフの `topN` で絞る

## S3. 期間コントロールで複数ペインを一括で切り替える

閲覧者がバーで期間を選ぶと、**その変数を参照する全ペインが同時に切り替わる**。
`controls` はビュー共通(全タブ)とタブ専用の 2 層に置ける(設定ファイル仕様 §2.2)。

```jsonc
"controls": [
  { "var": "period", "type": "date", "label": "対象期間", "default": "thisMonth",
    "presets": ["thisMonth", "lastMonth", "thisYear", "lastYear"] }
]
```

**推奨は単一変数形。** プリセット選択時、`@period` には kintone の相対日付関数が
**関数として**注入されるため、押し下がる。

```sql
SELECT ステータス, COUNT(*) AS 件数
FROM APP100
WHERE 受注日 = @period          -- DECLARE は書かない(バーが供給する)
GROUP BY ステータス
```

- **キャッシュとの相性が良い。**全ペインが同じ `@period` を参照すれば、押し下げ後の
  クエリも揃うので S1 がそのまま効く
- **任意区間(期間指定)に追従させたいペインは範囲形**で書く。半開区間にすること:

  ```sql
  WHERE 受注日 >= @period_from AND 受注日 < @period_to_next
  ```

  `@period_to_next` は**終了日の翌日**。`<= @period_to` は日時フィールドで終端日の日中を
  取りこぼす
- **単一変数形と範囲形を混ぜると、押し下げ後のクエリが変わるためキーが割れる。**
  1 つのタブでは書き方を揃える。混在させたい場合はタブを分け、タブ専用 `controls` を使う
- 単一変数形のペインは、閲覧者が**期間指定を選ぶと既定プリセットで動く**(関数で表せないため)。
  ペインに注意書きが出る

## S4. 押し下げを揃える / 割れる の対比

**単ペイン最適とダッシュボード全体最適が食い違う場面。**原則 3 は「押し下げろ」だが、
押し下がる条件が**ペインごとに違う**と、キーが分かれて取得が増える。

```sql
/* A: 揃う — 3 枚とも同じキー。取得 1 回 */
WHERE 受注日 = THIS_MONTH()
WHERE 受注日 = THIS_MONTH()
WHERE 受注日 = THIS_MONTH()
```

```sql
/* B: 割れる — 1 枚だけ押し下がる条件を追加。取得 2 回 */
WHERE 受注日 = THIS_MONTH()
WHERE 受注日 = THIS_MONTH()
WHERE 受注日 = THIS_MONTH() AND 部署 in ('営業1部')   -- ← これだけ別キー
```

```sql
/* C: 割れない — 追加した条件が押し下がらないので、REST クエリは A と同じ */
WHERE 受注日 = THIS_MONTH()
WHERE 受注日 = THIS_MONTH()
WHERE 受注日 = THIS_MONTH() AND 顧客名 LIKE '%商事%'   -- JS 評価。キーは変わらない
```

**どちらが良いかは件数で決まる。**

- 対象が小さい(数千件)なら **A / C** が有利。1 回取ってクライアントで分ける
- 1 ペインだけ極端に大きい範囲を見る、あるいは**その絞り込みで取得上限を回避できる**なら
  **B** が正しい。取得上限は全体最適より優先する(原則 5。集計は fail-closed)

**確認の手順**: MCP / CLI では `ksql_explain` で押し下げの有無を見る。プラグインでは
上の診断ログで `rest` と `cacheHit` を見るのが早い。

## S5. タブで段階を分ける — サマリーから分析へ

1 タブに 12 枚まで置けるが、**詰め込むと読めない**。「まず全体、次に内訳」はタブで分ける。

| タブ | 中身 | 条件の揃え方 |
| :--- | :--- | :--- |
| サマリー | KPI 4 枚 + 推移 1 枚 | 全部 `= @period` |
| 分析 | 部署別・担当者別・顧客ランク別 | 同じく `= @period`(タブ専用の絞り込みを足すならタブ側 `controls`) |

- **表示していないタブのペインは SQL を実行しない。**タブを開いた時に初めて走る
- キャッシュは**画面表示中は生きている**ので、タブを戻ったときは取りに行かない。
  破棄されるのは**再読込ボタン**と**自動更新**(`refreshSec`)のときだけ

## S6. できないこと — 集計結果はペインをまたげない

**一時テーブルも `SET` した変数も、そのペインの 1 回の実行内で消える。**
「重い集計を 1 ペインで作って、他のペインが参照する」はできない。

```sql
/* ペイン 1 で作っても… */
CREATE TEMP TABLE #集計 AS SELECT 部署, SUM(受注金額) AS 売上 FROM APP100 GROUP BY 部署;
SELECT * FROM #集計
```

```sql
/* ペイン 2 からは見えない(未定義エラー) */
SELECT * FROM #集計
```

- **同じ集計 SQL を各ペインに複製する**のが正解。重複しているように見えるが、
  取得は共有キャッシュが 1 回にまとめるので、実際に重いのは 1 回だけ。
  クライアント側の集計は残るが、集計後の行数は小さい
- 一時テーブルは**閲覧者のブラウザのメモリ**に載る。1 表あたり既定 10,000 行
  (500〜50,000 で設定可)、同時 16 表まで
- ペインをまたいで値を渡したいなら、**SQL ではなく期間コントロール(S3)**で条件を共有する

## 適用限界(スケール指針)

- 1 ペインの取得上限は既定 10,000 件(仕様案 §3.3)。**上限に達したら集計はエラー**になるため、
  WHERE の期間・部署条件で対象を上限内に収める。**明細は打ち切って表示**される(原則 5)。
  いずれもペインのタイトルに警告アイコンが出る。
  **例外は `SELECT COUNT(*)`** で、上限を適用せず 1 リクエストで総件数を返す(原則 5)。
- 同一アプリで**押し下げ後の kintone クエリが同じ**なら、ペインが何枚あっても取得は
  共有キャッシュで 1 回に統合される(仕様案 §5)。**同じ SQL である必要はない** — 揃えるのは
  押し下がる WHERE。参照する列が違うと和集合で取り直しが入ることはあるが、ペイン数ぶんは増えない。
  設計は **S1**、揃える / 割れるの対比は **S4**、実測の手順は S 系列冒頭を参照。
  ペイン間で WHERE を揃えるほど効率が良い。
- 明細表(D8)以外のペインで LIMIT なしの明細 SELECT を書かない(設計原則 1)。
